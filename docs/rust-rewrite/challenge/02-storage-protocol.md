# 02 Storage protocol review (reviewer B)

Labels: read (file:line or URL), measured (I ran it), inferred, guess. Sources for object_store: crate tarball 0.14.2 from static.crates.io, unpacked in my scratchpad (`B/os/object_store-0.14.2`). R2 docs fetched 2026-11-07 as markdown from developers.cloudflare.com.

Ledger: ack parent note (curl allowed). Fetched via curl on 2026-11-07, all labelled read (URL).

## Verdict

The pieces -> manifest -> current.json shape is sound and matches how Iceberg and Delta commit. Three things in section 7.2 and 12 do not survive contact with the sources. D9 (`Content-MD5` on every PUT) cannot be done through `object_store` 0.14.2. The 412 path on `current.json` is underspecified and mishandles a lost reply, so a successful commit can look like a failure. The full-manifest rewrite is quadratic and the design's own "bounded by pieces" claim hides a 450x to 850x cumulative cost at the tail. The global `objects/<sha>` namespace is defensible but should be a conscious decision, because it makes per-session deletion a reference-count problem the writer cannot answer.

## Findings

### Blocker

**B1. `Content-MD5` per PUT is not available through `object_store` 0.14.2 (DESIGN 7.2, 10, 12, D9).**
- Design: PUT with `Content-MD5` computed locally, "R2 rejects on mismatch". Crate row says `object_store` does R2 PUT, GET, LIST, conditionals.
- Problem. `PutOptions` carries mode, tags, attributes, extensions. `with_attributes` maps only CacheControl, ContentDisposition, ContentEncoding, ContentLanguage, ContentType, StorageClass, Metadata (read `src/aws/client.rs:374-388`). There is no Content-MD5 attribute. The only Content-MD5 in the crate is the mandatory header on DeleteObjects (`client.rs:591-597`) and a probe in `builder.rs:1549`. The crate's integrity option is `with_checksum_algorithm(Checksum::SHA256 | CRC64NVME)`, which sends `x-amz-checksum-sha256` or `x-amz-checksum-crc64nvme` computed over the payload (`client.rs:427-445`; `builder.rs:1025`). The crate computes it from the bytes it is handed, so it proves transport integrity from the handed buffer, which is what the design wants. But whether R2 honours `x-amz-checksum-*` on single PutObject is not confirmed: the R2 S3 compatibility table lists `Content-MD5` for PutObject and does not list any `x-amz-checksum-*` row for PutObject (read, https://developers.cloudflare.com/r2/api/s3/api/ , PutObject row). The page has a "Checksum Types" table (CRC64NVME full-object; CRC32, CRC32C, SHA1, SHA256 composite) but that reads as a multipart-and-copy matrix. I could not confirm single-PUT SHA256 enforcement without touching R2.
- Also: by default the crate computes a SHA-256 of the payload for SigV4 signing unless `skip_signature`/unsigned payload is configured (`client.rs:422-424`). That is a second full hash of every body, CPU cost not in section 8's 20 ms target. Over HTTPS use `UnsignedPayload` (`builder.rs:314-316`).
- Industry. aws-sdk and rclone set `Content-MD5` or `x-amz-checksum-*` per request; restic verifies via the backend's MD5 on S3 upload.
- Change. Either (a) keep `object_store` for GET, LIST and `current.json` and write pieces through a thin signed `reqwest` PUT that sets Content-MD5, or (b) configure `with_checksum_algorithm(SHA256)` and test in slice 2 against the acceptance namespace that R2 rejects a deliberately wrong checksum. Until one is proven, strike D9 from the decision log as an implemented control and say "unverified". A 20-line probe in slice 0 settles it.

**B2. Lost reply on `current.json` turns success into a spurious 412, and the recovery text is wrong (DESIGN 7.2 last paragraph, 3.5, 10).**
- Read: `put_opts` with `PutMode::Update` sets `retry_on_conflict(true)` but not `idempotent(true)` (`src/aws/mod.rs:274-300`); `PutMode::Overwrite` is the only idempotent mode. In the retry loop, transport `Timeout` and `Interrupted` are retried only if idempotent (`src/client/retry.rs:435-441`). So a dropped connection after R2 committed surfaces as an error to the caller (good, not silently retried). But server 5xx, 429, 408, and 409 are retried unconditionally for the same request (`retry.rs:405-412`). A 5xx returned after R2 committed (gateway error after write) is retried with the same `If-Match: <old etag>`, and that retry returns 412 although our write is the one that won. Default `max_retries` and 3-minute `retry_timeout` apply (`retry.rs:249-257`).
- Consequence in the design: the caller sees `Error::Precondition` and, per 7.2, "re-reads current.json, rebuilds the manifest from its contents plus ours, retries once". After an ambiguous success, the re-read returns our own manifest. "Plus ours" then duplicates our pieces (or, if the rebuild is naive, forks epochs), producing a manifest that differs from the one already referenced by `current.json`.
- Also the vendor note the design cites: a `NoSuchKey` read after a lost reply is "not final" (found: https://developers.cloudflare.com/r2/reference/consistency/ , "A strongly consistent read ... that returns `NoSuchKey` (404) ... is **not** final with respect to an earlier `PutObject` whose outcome is still unknown ... may still commit after the negative read has returned"). This applies to piece and manifest PUTs: a lost-reply PUT can land after the writer has already decided the key is absent and moved on. With content addressing that is harmless (same bytes). It is NOT harmless for `current.json` with If-Match: a delayed in-flight conditional PUT with an old ETag can still commit after a newer one is read, but only if its precondition still holds, and since the ETag changed it will fail 412. So the fence holds; the danger is only the misdiagnosis above.
- Industry. Iceberg's commit and Delta's `_last_checkpoint` both treat "commit state unknown" as a distinct outcome and verify by checking whether the new snapshot id is reachable from the current head before retrying (Iceberg `SnapshotProducer` cleanup rule: do not delete new files when `CommitStateUnknownException`; https://iceberg.apache.org/spec/#commit-conflict-resolution-and-retry, and Iceberg Java `CommitStateUnknownException`).
- Change. Write the rule down: on 412 or any error from the `current.json` PUT, GET `current.json`. If its manifest hash equals the hash of the manifest we just wrote, the commit succeeded; stop. If it equals our `previous`, the PUT never landed; retry. Otherwise it is another writer; merge. Add that "unknown outcome" state to the Disposition enum and to Hegel property 4 (fake store must inject "committed, reply lost" and "committed, then 5xx retried").

### Major

**M1. Rebuild-and-retry-once is underspecified and "once" is wrong (DESIGN 7.2, 3.6 Idempotence).**
- Who can hit one session key? Inferred from the design: (1) two daemons on one host during a launchd or systemd restart overlap; the old process is still finishing a capture. (2) Reinstall or restore of `~/.config` and the index on another machine with the same `MachineId`. (3) A copied disk image or VM clone. (4) The operator's own `memory reconcile` CLI run beside the daemon (section 4 lists it as a subcommand). (5) A manual rerun after a quarantine. The text "both hosts write distinct session keys" only covers the intended topology; session ids are agent-generated UUIDs, and Claude's `--resume` or Codex forks can in principle repeat a session id on two machines but `machine` is in the key, so only the cases above collide. Index loss on one machine is covered by "one GET per session" only if the ETag is rebuilt from `current.json` (it is, 8.3).
- Retry once is wrong because 412 can repeat under legitimate contention (case 1, 4) and the second failure falls through to an unspecified state. Iceberg retries with exponential backoff up to `commit.retry.num-retries` (default 4), re-applying its change to the refreshed base each time, and fails the commit with a conflict exception beyond that (https://iceberg.apache.org/docs/latest/configuration/#table-behavior-properties). A bounded loop with jittered backoff and a hard failure (quarantine the session, not the source) is the established pattern.
- "Rebuild the manifest from its contents plus ours" is not defined. Whose epochs win? If the other writer advanced epoch 2 and we have epoch 2 pieces too, merging would interleave unrelated byte ranges. For a single-writer-per-session design, a 412 that is not our own success means a second writer exists, which is a configuration fault. The safe action is not to merge. Change: on a foreign 412, do not rebuild; quarantine the session with both manifest hashes, count it, and let the operator decide. That removes the merge logic entirely (R8) and matches the design's own claim that a session has one writer. If merging is wanted, specify it per property.
- Also check `previous` linkage: the manifest has `previous`, but nothing states it is compared to `current.json`'s manifest on commit. Add that as the invariant the fence protects.

**M2. Full manifest rewrite per capture is quadratic in stored bytes, and the design states only the final size (DESIGN 6, 3.2).**
- Measured (probe, synthetic JSON, realistic piece record with sha256, object key, encoded_len; my probe `B/probe` run inline): per-piece JSON is about 216 to 226 bytes. Final manifest size and cumulative bytes PUT if every capture rewrites the full manifest:

| Pieces | Final manifest | Cumulative manifest bytes per session | Ratio to final |
|---:|---:|---:|---:|
| 51 (p99, 60 s) | 11.5 KB | 0.30 MB | 26x |
| 87 (p99, 30 s) | 19.3 KB | 0.85 MB | 44x |
| 898 (max, 60 s) | 194 KB | 87 MB | 450x |
| 1,700 (max, 30 s) | 368 KB | 313 MB | 850x |

- Compare: the worst session's data is a few tens of MB of pieces. At 898 pieces the manifest overhead is comparable to, or larger than, the payload it describes. Request counts are fine. Egress is free and ingress is free on R2, so this is a latency and CPU cost on the host (JSON serialization, SHA-256, upload of up to 368 KB every 60 s) and a read cost for any reader that fetches historical manifests, not a dollar cost. Storage: 313 MB at 0.015 USD/GB-month is under 0.005 USD, immaterial. This is "inferred from measured sizes", not a dollar problem. The design should say so and drop the word "bounded".
- Also the manifest includes all retained epochs of every append source (6, "Class append retains every epoch"), so a long-lived session with replays grows further.
- Industry. Iceberg: manifest list -> manifest files; a commit writes one new manifest and a new manifest list that reuses older manifests (https://iceberg.apache.org/spec/#manifests). Delta: a JSON commit file per version plus periodic checkpoints (https://github.com/delta-io/delta/blob/master/PROTOCOL.md#checkpoints). Both exist because rewrite-all is quadratic.
- Change, small. Keep one manifest object per capture but make it a delta: `{previous, sources: [new pieces only]}`, chained via `previous`, with a full "checkpoint" manifest every N captures (say 64). The reader walks back to the last checkpoint. That is the Delta shape, costs one extra field, and the `previous` field already exists. Risk removed: measured quadratic cost at 898 and 1,700 pieces. If the operator prefers simplicity, accept the cost explicitly and cap by writing a full-consolidation epoch, but record the choice.

**M3. Global `objects/<sha>` is a coupling the contract does not mention (DESIGN 6; hypothesis 1).**
- Read: contract goal is session-local publication (`docs/session-capture-contract.md` header; DESIGN preamble). DESIGN 3.6 and 16.2 push retention and post-hoc privacy deletion to a later project "which on an immutable store means deleting objects".
- Problem. If two sessions emit identical encoded bytes they share an object. Realistic cases here: identical config snapshots (`claude.config`, `pi.settings` across sessions on one host), empty or tiny files, Codex mirror content, subagent files copied between parent and child, and the same shared-store whole captures (16.1). Deleting one session's data (privacy exclusion after the fact, the DDIA "limitations of immutability" passage the design itself quotes) requires knowing no other manifest references the object. That needs a full scan of all manifests (a LIST of `sessions/**` plus a GET per manifest chain). Nothing in the layout supports it cheaply and the writer cannot do it.
- Industry. restic, borg and git are single-repo dedup stores where global content addressing is the point, and all three accept mark-and-sweep GC that reads every index (`restic prune`, `borg compact`, `git gc`); restic notes that `forget` does not delete data until prune and that prune needs exclusive access (https://restic.readthedocs.io/en/stable/060_forget.html). Iceberg and Delta keep data files under the table and delete via orphan-file removal that lists the table location and subtracts referenced files (https://iceberg.apache.org/docs/latest/maintenance/#delete-orphan-files), scoped per table. OCI registries share blobs across repositories and GC by mark-and-sweep with the registry in read-only mode (https://distribution.github.io/distribution/about/garbage-collection/). All of them pay the cost because cross-owner dedup saves real space. Here the measured saving is not shown.
- Would session-scoped keys cost anything? Inferred: dedup savings across sessions are not measured in the design; most pieces are unique transcript bytes. Cost of scoping is only the duplicated small config files and storage at 0.015 USD/GB-month. `If-None-Match: *` still works per key. Deletion then becomes a prefix delete of `sessions/<...>/<session>/objects/`, free on R2, no GC, and it matches the contract goal literally.
- Change. Measure first: count duplicate encoded-object hashes across this Mac's sessions with a throwaway script over the experiments data (not a transcript read, just hash counts on the offline timeline). If dedup share is small, key objects as `sessions/<archive>/<machine>/<agent>/<session>/objects/<sha>.zst`. If the operator keeps the global namespace, write the deletion rule now: objects are never deleted unless an offline mark-and-sweep proves zero references.
- Rating note: Major, not Blocker, because the design explicitly defers deletion. It is Blocker-grade if the privacy owner (reviewer E) requires post-hoc deletion.

**M4. Key by hash of encoded bytes ties identity to zstd (DESIGN 6; hypothesis 2).**
- Read: key is "sha256 of encoded bytes". The manifest also records the raw piece `sha256` (6), so both digests exist.
- Problem. zstd output is stable for a given library version, level, and params, but not guaranteed across versions. Same raw bytes can produce a different key after a `zstd` crate bump (zstd's own docs state the compressed format is stable and decodable, but the compressor output is not contractually deterministic across releases; https://github.com/facebook/zstd/blob/dev/doc/zstd_compression_format.md and release notes where compression ratios and strategies change). Consequences: (1) re-capture after a crate upgrade re-uploads bytes already stored (R6 cost and duplicate objects, harmless but wasteful); (2) the "replay whole object" idempotence, R4 "converges to the same R2 state", is false across versions because the state differs; (3) the 7.2 whole-capture double-pass ("if the second pass yields a different digest, the file moved") conflates source movement with encoder nondeterminism; multithreaded zstd (`nbWorkers`) can also vary output by job size, though the design does not enable it; (4) pieces cannot be verified from the manifest by a reader without storing encoded digest separately, which the manifest does not carry (`encoded_len` only).
- Industry. git and restic key by hash of the uncompressed content (git: object id is over the uncompressed payload with header; restic: blob id is SHA-256 of plaintext, then encrypt and compress). Iceberg and Delta key data files by writer-chosen unique names plus recorded checksums. OCI blobs are addressed by digest of the stored layer and carry the uncompressed diff id separately; that is the one registry system keyed by encoded bytes, and it works because layers are never re-encoded by the registry.
- Change. Key by raw sha256 plus length: `objects/<raw_sha256>.zst`, and record `encoding: "zstd"`, level, and `encoded_sha256` in the manifest piece. A re-encode with a new crate then hits 412 and is a no-op, as intended by R4, and the key can be computed before compression (removes the first "learn the key" pass in 7.2 Capture whole, saving one disk read and one compression pass of 103 MB sources). Trade-off: the stored bytes under an existing key may differ from what this writer would produce. That is fine because the reader decodes and verifies the raw digest. If end-to-end MD5 is kept (B1), it is the encoded-bytes check; the key is the identity.

**M5. Listing is on several hidden paths (DESIGN 10; hypothesis 6).**
- Read. `memory status` "computes pending as disk minus index minus R2" (10, last para). Quarantine discovery needs `quarantine/` listing (6; "visible to both hosts"). Measure 1 under "Bugs in this writer" says bug-period manifests are "findable by one list". But manifests are keyed `manifests/<sha>.json` with writer version inside the body; a LIST returns keys and sizes only, not contents. Finding manifests by writer commit therefore needs LIST then GET of every manifest in the bucket. "One list" is wrong. Correct: one LIST plus N GETs, or an index keyed by writer version (e.g. `manifests/<writer_version>/<sha>.json`), or a per-version marker.
- Cost. LIST is Class A at 4.50 USD per million, 1,000 keys per page (https://developers.cloudflare.com/r2/pricing/). With roughly 4,621 sessions and p99 51, mean far lower, the manifest count is on the order of 27,481 captures (3.2) per measured window. LIST of the manifests prefix is under 30 requests, trivial; the GETs are 27k Class B at 0.36 USD per million, about 0.01 USD. Dollar cost is negligible. The real cost is latency and the absence of any consistent snapshot index. R2 lists are strongly consistent (https://developers.cloudflare.com/r2/reference/consistency/ , Object listing row), so discovery is correct, not stale.
- `status` pending: needs session-level GET of `current.json` for every active session, or a LIST of `sessions/<archive>/<machine>/`. 4,621 GET per status call is 0.002 USD; fine but not "computed", it is slow and unbounded as sessions grow. Prefix LIST returns no ETags beyond the listing but R2 lists include ETag, which could be compared to the index's cached ETag (inferred; list entries carry `ETag` in S3 ListObjectsV2). Say so.
- Change. Correct the "one list" wording and either encode the writer version in the manifest key path or accept list-plus-get. Note that `objects/` must never be listed by readers (3.6 says so) but the future GC needs it.

### Minor

**m1. 409 versus 412 surfacing is handled, but document it (DESIGN 6, 12).** `PutMode::Create` sends `If-None-Match: *`; 412 and 304 are both mapped to `Error::AlreadyExists` (`src/aws/mod.rs:260-271`, comment citing R2). Generic 409 also maps to `AlreadyExists` (`retry.rs:171`), so a 409 from a concurrent delete reads as "already stored", which is a false success if the object was deleted. Only reachable once a delete path exists. The `If-Match` path converts `NotFound` to `Precondition` (`mod.rs:281-299`), so a deleted `current.json` looks like a 412 conflict, not "recreate". Handle: after any `Precondition`, re-read.

**m2. `PutMode::Update` and the `PutResult` ETag.** `do_put` returns the new e_tag through `get_put_result` (`client.rs:485-491`), so the ETag for the next If-Match comes from the response. Lost reply means the new ETag is unknown; GET it. Another reason for the verify-by-reading rule in B2.

**m3. R2 write-rate limit.** R2 allows 1 concurrent write per second to the same key; faster returns 429 (https://developers.cloudflare.com/r2/platform/limits/ , footnote 5). `current.json` is written at most every quiet window, so fine, but retry-on-429 on `current.json` interacts with B2.

**m4. "Multipart has no conditionals" is consistent with R2 docs.** read (https://developers.cloudflare.com/r2/api/s3/api/index.md): the CompleteMultipartUpload row lists no If-Match/If-None-Match support, while PutObject lists both. Conditional headers are documented on PutObject and CopyObject destination only (https://developers.cloudflare.com/r2/api/s3/extensions/ , read). Claim stands as "not documented". Not on the critical path.

**m5. 5 MiB multipart minimum and 10,000 part limit confirmed** (https://developers.cloudflare.com/r2/platform/limits/ ; https://developers.cloudflare.com/r2/objects/upload-objects/). Irrelevant at these sizes.

## Open questions for the operator

1. Is post-hoc deletion of one session's bytes a requirement within a year? If yes, session-scoped object keys (M3) become mandatory.
2. May the writer use a hand-rolled signed PUT for pieces if `object_store` cannot do Content-MD5 (B1)?
3. On a foreign 412 for one session key, is quarantine-and-stop acceptable instead of merge (M1)?
4. Is a delta manifest chain with checkpoints acceptable, or is one-GET reads a hard requirement (M2)?
