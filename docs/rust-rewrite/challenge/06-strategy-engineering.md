# 06 Strategy and engineering review (reviewer F)

Labels: read (file:line or URL), measured (I ran it), inferred, guess. Probe dir: scratchpad `F/hello` (trivial Rust binary, synthetic).

## Verdict

The design is strong on capture mechanics but weak on delivery strategy. Its slices cannot reach the acceptance AGENTS.md demands, because no slice builds a reader (Blocker). Nothing compares the new writer with the running Go candidate before cutover (Major). The 2 ms hook target is not testable with the stated approach and is unsupported by the one measurement I made. The core test gate depends on a beta crate with a stated fallback; that is acceptable only if the fallback is made a slice 0 exit criterion. Several items are over-built for two hosts and one operator.

## Findings

### Blocker F1. No slice delivers a reader, so no slice can reach acceptance
- Claim: DESIGN.md:39-41 puts reading, export, restore and analytics out of scope; D7 (line 17 table) ends scope at `current.json`. Slices 0-3 (DESIGN.md:~565-585) contain no reader.
- Problem: AGENTS.md says release acceptance includes "actual writer output -> reader -> importer -> event index -> report", and the contract wants one authoritative reader. The new layout (`objects/`, `manifests/`, `current.json` with epochs and pieces, DESIGN.md:236-290) differs from the Go `session-reader/v2` export (07-consumer-reader.md: heads wire, `capture-v1 export`, Python mirrors of the Go validator). Reader-side checks the design relies on are also deferred to it: "the reader project verifies digests on read" (DESIGN.md:439). The design's own D10 read-back sample (DESIGN.md:462-466) is an unnamed mini-reader inside the daemon, so a reader is already needed, in the wrong place.
- Evidence: read, as cited. 07-consumer-reader.md finding 2 says even the Go candidate has no true restore, only `export`; "one reader" is intent, not fact.
- Industry: Kafka Connect/Debezium sources are accepted against a sink or consumer test (Debezium integration tests consume from the topic), and restic/borg treat `restore`+`check` as part of the backup tool, since a backup that has not been restored is unproven.
- Recommend: add a slice between 2 and 3 (call it 2b): a minimal Rust `memory-reader` library plus `memory restore <session> --out DIR`. It does `GET current.json -> GET manifest -> GET pieces`, verifies each piece digest, per-epoch sha256 and manifest digest, and writes the reassembled bytes per epoch. That is about the same code as the D10 read-back sample, so build it once and have the daemon call it. Exit criterion: restore of every captured session from the acceptance namespace equals source bytes. A JSON export producing the existing `session-reader/v2` envelope is the second step; the Python importer and the writer->importer->index->report gate then run against it unchanged. Defer new analytics, but keep the gate. Without this the project cannot be called accepted under AGENTS.md. State explicitly that D7's "out of scope" means "analytics redesign", not "no reader".

### Major F2. No shadow/parallel run against the Go candidate; hard-won edge cases lack counterparts
- Claim: slice exit criteria (DESIGN.md:~565-585) are green gates and "totals matching section 3" (a simulation of Mac timelines). Cutover is "not part of these slices".
- Problem: the Go work found most real defects live, not in tests. 05-history-lessons.md finding 3: five live activations each found a new production defect that 62k lines of tests missed (deleted-source hint crash loop L7; enrichment spin L8; idle CPU Q8). Spolsky's rule ("Things You Should Never Do, Part I", joelonsoftware.com 2000) and the second-system effect (Brooks) apply: old code encodes bug fixes whose reasons are invisible. Rewrite design here is a fresh mechanism, so the mapping from old fixes is not automatic.
- Edge cases in 04-tests.md / 05-history-lessons.md with no DESIGN.md counterpart (read; checked by grep of DESIGN.md for each term):
  1. Secret scrubbing/redaction of config, env, command lines, backups (P1-P3, PR #14). DESIGN.md has a policy token (R2) but no scrubber or secret filter spec; grep for scrub/redact/secret finds nothing.
  2. R2 key length 1,024 bytes (I4): stated as a fact (line 119) but no admission check or typed outcome.
  3. Request timeouts scaled to object size (L2/GAP-02, 30 s total made 75 MB unpublishable). DESIGN.md has retry backoff but no timeout rule; sources reach 103 MB.
  4. Source cap per session (L4, 1024 sources, rewrite-heavy sessions) and inventory caps (L3).
  5. `immutable=1` SQLite ignoring WAL (D7); only "SQLite backup API" is named at DESIGN.md:7.3. The source-changed vs backup-failed error split (D8).
  6. Orderly shutdown must not spend retry budget (L6); Run must not exit on item-level errors (C5). Error scope typing is not in section 5 beyond `Disposition`.
  7. Machine-id creation race (D3), file modes 0600 for state (D4). Identity stability when sibling dirs appear (I1), `/var` vs `/private/var` (I2).
  8. Battery sleep/clamshell (L12) and AC-power-dependent gate runs.
  9. Crash tests must delete the source after the committed boundary (D9/T1) so recapture cannot mask loss. DESIGN.md property 4 has crash-before/after-put events but no "source removed" step in the state machine, so the same masking is possible.
  10. Codex mirror pairing and lone surrogates (G3, G4): reader-side, relevant to F1.
  11. Shared-store exclusion denying all Codex resources (P5): DESIGN.md 16.1 adopts the same default, which produced 7,909 `policy_denied` issues. Known bad, adopted anyway.
  12. Quadratic epoch retention (Q9): `~/.claude.json` 206 epochs in 8 days; Codex store 1,232 MiB encoded over 6 epochs. DESIGN.md 6 retains every epoch for append class and, for the snapshot class, only the latest, but shared stores and `history.jsonl` are `append`-like in some cases; the manifest is rewritten in full per capture (6:276-278) so its size grows with all epochs; the 898-piece worst case is from the sim, not from epoch-heavy files.
- Industry: strangler fig (Fowler, martinfowler.com/bliki/StranglerFigApplication.html) and GitHub Scientist (github.com/github/scientist) run old and new side by side and compare. Here that is cheap: the Rust daemon is read-only on sources and can write to a separate namespace.
- Recommend: make "shadow run" a slice 2 exit criterion. Run the Rust daemon for at least 7 days on the Mac (then BC-01) into the acceptance prefix, with a comparer that, per session, checks that the bytes reassembled from Rust `current.json` equal the Go candidate's exported latest epoch and the local file. Add a one-page "Go fix -> Rust counterpart" table (items above) as a slice 1 exit artifact; any row marked "not applicable" needs a reason.

### Major F3. Slice 2 can write to production R2 without cutover controls
- Claim: slice 2 includes `object_store` "against the acceptance namespace" (DESIGN.md:~575) and exits on "a day of this Mac's sessions captured".
- Problem: "acceptance namespace" is not defined anywhere (grep: only in slice 2). Section 6 keys have no namespace prefix; `archive` is in only the session key, not `objects/` or `manifests/`. If the Rust daemon uses the production bucket with a different archive id, it still shares `objects/` and `manifests/` at bucket root with anything else, and could race the Go candidate's layout. AGENTS.md: R2 reset is gated by an inventory/validation/cutover sequence; the 2026-11-07 permission does not mean a reset happened.
- Recommend: define in section 6 a bucket-level or archive-level namespace, ideally a separate bucket for slices 2-3 with scoped credentials (write only to that bucket), and state that production bucket access begins only at cutover. Say who deletes the acceptance data.

### Major F4. Hegel as the core gate: beta dependency, fallback not exercised
- Evidence (measured via crates.io API): hegeltest 0.52.0, created 2026-03-16, last update 2026-11-03, 255 versions in about 8 months, 1.63M downloads, repo hegeldev/hegel, "built on Hypothesis". proptest 1.12.0 (created 2017, 236.8M downloads, updated 2026-10-10); proptest-state-machine 0.9.0 (3.9M, updated 2026-10-10); bolero 0.13.7 (6.4M). So hegeltest ships roughly one release per day on average. The project's own text says "Beta, breaking changes possible" (DESIGN.md:12 table).
- Problem: properties 1-6 (DESIGN.md:~540-560) are the correctness argument; a breaking API change or an engine bug lands in the gate. R8 says well-known crates; Hegel is not yet. The static-engine feature was probed only on Mac (16 s build; DESIGN.md 3.4, 16.3). I did not verify its state-machine support or shrinking quality beyond what Hypothesis is known for [guess; not read from hegel docs]. Hypothesis's integrated shrinking and stateful testing are the strongest in the field, which is the real argument for Hegel, but the design never states it.
- proptest comparison (read from memory, labelled guess): proptest shrinks by strategy value trees; `proptest-state-machine` gives model-based sequence shrinking including removal of transitions, which maps to property 4. Known weaker points: shrinking can be slow with complex strategies and it does not persist a database as Hypothesis does (it has a regression file).
- Recommend: pin `=0.52.0` exactly, vendor or lock, and make the proptest fallback a tested path, not a contingency: write properties 1 and 4 once in proptest-state-machine in slice 1 and keep it as a cross-check, since the model (a fake R2 and a pure planner) is the same. Add BC-01 Hegel build to slice 0 as an explicit blocking exit (it is "the first gate task", section 0.4, good). A 500-case CI run against a randomly seeded engine without a recorded seed is not reproducible; record the seed on failure.

### Major F5. 2 ms p99 hook budget is not shown, and is probably not reachable with measurement at that precision
- Claim: agent blocked in a hook, p99 2 ms (DESIGN.md:~477 table); asserted in slice 2.
- Measured: a trivial release Rust binary (428,720 bytes, std only, appends one line to a file) spawned 500 times from Python `subprocess.run`: p50 3.02 ms, p99 10.80 ms. `/usr/bin/true` the same way: p50 2.06 ms, p99 2.62 ms. So spawn overhead alone (fork/exec via Python) is about 2 ms at p50 on this Mac; the Rust binary adds about 1 ms at p50 and the p99 tail is 4x higher. This includes Python's spawn cost and macOS exec/dyld/code-signing checks, so it is an upper bound on the binary's own cost, not a clean number. It does show the target cannot be asserted as "wall time of the spawn" at 2 ms p99 on macOS.
- Problem: the hook's cost to the agent is what the agent's own spawn measures; the design controls only the binary's runtime after exec. `memory hook` will also link clap, serde_json, tracing; those add startup cost (guess: small, hundreds of microseconds), unmeasured. Linux numbers differ (vfork/exec ~0.5-1 ms; guess).
- Recommend: redefine the metric as "time from main() entry to exit" measured in-process plus "bytes appended and syscalls count" asserted by strace/dtruss-style counter test, and a separate informational spawn-latency benchmark (hyperfine) compared against `/usr/bin/true` on the same host. Keep `memory hook` as a separate minimal binary or a `main` that parses argv by hand before touching clap/tokio (tokio is not initialised in hook anyway, as the design says). Drop "p99 2 ms" or state it on Linux only after measurement.

### Major F6. Tokio multi-thread for at most 8 uploads is not justified under R8/R5
- Claim: one tokio multi-thread runtime with two workers; `spawn_blocking` for hashing; at most 8 uploads in flight (DESIGN.md:11).
- Problem: the workload is: a handful of concurrent PUTs of 59 KB median, plus blocking file reads, hashing, zstd, and notify (which uses its own threads and std channels). Async buys nothing here except that `object_store` is async-only (read, 02-storage-protocol.md per README ledger). Tokio's blocking pool defaults to 512 threads max and each idle thread costs stack address space (not RSS) [inferred]. Two worker threads plus the blocking pool plus notify's thread plus hyper/rustls connection tasks gives a larger moving part count than a thread pool.
- Alternatives (read/inferred): `rusty-s3` 0.11.0 (crates.io, updated 2026-10-27) is a sans-IO presigner: it builds signed requests, and you send them with `ureq` (blocking, rustls). Conditional headers can be included in signed headers [inferred; check]. That removes tokio, hyper, tower, aws-config; and Content-MD5 can be set freely, which `object_store` 0.14.2 reportedly does not support (B1 in 02-storage-protocol.md, accepted by the parent). `aws-sdk-s3` 1.157.0 supports `If-Match`, `If-None-Match` and `Content-MD5` natively but is large (many generated crates; build time and binary size are known to be heavy, tens of MB of debug and about 10+ MB release on typical use [guess; unmeasured]). `object_store` itself pulls reqwest/hyper/tokio.
- I could not measure binary size or RSS of these in the time given (cargo works offline? no, I did not build with the dependencies). The 40 MB RSS target at 30k sources is plausibly dominated by the index (30k SourceState with 108-byte hasher state plus pieces Vec) rather than the runtime, but unmeasured [inferred].
- Recommend: before slice 2, a 1-day spike building the PUT path with `rusty-s3` + `ureq` in a thread pool (4 threads) versus `object_store` + tokio, measuring release binary size, RSS during 8 concurrent PUTs, and ease of Content-MD5/If-Match. Choose the blocking one if it passes; it also makes crash-injection testing simpler (no async cancellation). The core crate is already synchronous, so the cost of deferring is low.

### Minor F7. Lint table: friction with the byte-offset code
- Claim: `indexing_slicing`, `expect_used`, `unwrap_used`, `panic` deny; `allow_attributes` deny; `missing_docs` deny in CI (DESIGN.md:13).
- Problem (inferred, standard clippy behaviour): `indexing_slicing` fires on every `buf[a..b]`, which is most of the piece/offset code; every one needs `.get(a..b).ok_or(..)?` or an `#[expect]`. Offsets are already validated by `Offset` newtypes, so a runtime check duplicates the invariant. `missing_docs` deny forces docs on every pub item in a binary-plus-two-crate workspace with no external API; `missing_errors_doc` likewise. `unwrap_used` and `expect_used` conflict with Mutex lock and tests (design carves out tests). Clippy's own docs list `indexing_slicing` as `restriction` (opt-in) because it is noisy (rust-lang.github.io/rust-clippy/master/index.html#indexing_slicing).
- Industry: small teams (ripgrep, fd) enable few restriction lints; the strict "deny panics" posture is seen in firmware or sec-critical code (e.g. Android's Rust guidance prefers avoiding panics but does not ban indexing). Cost is real: expect_with_reason is cheap, but slicing churn is not.
- Recommend: keep `unwrap_used`, `panic`, `unsafe_code=forbid`, `allow_attributes`; confine `indexing_slicing` to a `slice` helper module that returns `Result`, and downgrade `missing_docs` to `warn` outside `memory-core`. State a budget: more than N `#[expect]` for one lint means revisit.

### Minor F8. Over-engineering candidates (R8)
Candidates for deletion or deferral, with the measured risk each removes or does not:
1. Monthly `cargo-mutants` and `cargo-llvm-cov` floor: 04-tests.md finding 5 says gremlins earned its cost once, with zero production defects since and about 1,240 lines of mutant-killing tests. Keep one run at end of slice 1; delete the monthly cadence. Coverage floor "current percentage" is a ratchet that rewards pinning tests (04-tests.md finding 7 says drop coverage-driven tests).
2. `schemars` + generated JSON Schema + CI drift check (DESIGN.md:288-291): the only consumers are Rust (writer, reader) and Python's `jsonschema`. With F1 solved by a Rust reader, schemars is unneeded in the writer until a non-Rust consumer exists. Keep property 6 (round-trip, unknown schema rejected).
3. Daily independent full re-hash plus daily read-back of ten sessions (D10, DESIGN.md:454-466): the re-hash catches bugs in resumable state, which is a risk the design itself created by choosing `sha2` `SerializableState` (internal byte format, version-pinned). The alternative with no new mechanism: hash the delta only for the upload key and whole-file digest recomputed at each epoch start only. I would keep the re-hash (cheap, 70 ms/19 MB) and replace the read-back sample with the F1 `memory restore` run by cron on one session; same coverage, no daemon code path.
4. `writer.commit` in every manifest: manifests hash-keyed per content mean identical captures under different writer versions produce different manifests, so the "reconcile twice makes zero PUTs" property needs the writer field excluded or the PUT skipped by index. Check, otherwise upgrades re-PUT everything [inferred; no evidence].
5. Learned roots, pending launch evidence, per-session ETags in the index "rebuildable": a rebuildable cache that holds non-rebuildable data (hook launch evidence exists only in the hint log, and the log is rotated and deleted after 10 s, DESIGN.md 8.2). Either not rebuildable or launch evidence is lost on index loss; the claim "deleting it loses nothing" (8.3) is false for launch evidence and the hint offset. This is design inconsistency, listed here, also relevant to reviewers A/D.
6. `Authorized<T>` capability token and `Disposition` enums are fine; the full 19 `SourceKind` variants in 5 can wait until slice 3 for non-transcript kinds.

### Minor F9. Slice ordering and exit criteria
- Slice 2 does "append-class sources for all three agents" but R1's 14 kinds and the Codex/Pi launch evidence arrive in slice 3, after footprint targets are "asserted in slice 2": footprint at 30k sources needs the snapshot classes (SQLite stat/backup, config scrubbing) and BC-01. Targets measured at slice 2 will be re-measured in slice 3; say so.
- Slice 1's exit "properties green at 2,000 cases locally" is not an acceptance gate; use the model-history coverage-guard idea from 04-tests.md (fail if the generator never produced multi-epoch, restart, crash-after-manifest) so properties are not vacuous. Properties 1-6 as written have no such guard.
- Property 4's fake R2 must model lost-reply (PUT applied, error returned) and 412 on `If-None-Match`; the design's list `crash-before-put/after-put/after-manifest` omits lost reply, which was the root of D1/D2 in the Go history.
- Process: add the "Go fix -> Rust counterpart" table (F2) and a restore test (F1) as exit criteria; define "acceptance namespace" (F3).
