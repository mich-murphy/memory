## C2. Object-key hashing: PARTLY CONFIRMED. Code and DESIGN disagree on order; code is the safer one. Confidence high on code, medium on design intent.
- DESIGN.md:371: "`objects/<sha256 of raw piece bytes>.zst`. ... A 412 means the object is already stored, which is success." DESIGN.md 7.3 steps 2-6 (lines 562-570): hash "raw bytes" (step 2), then transform (3), compress and "digest the encoded bytes" (4), PUT `objects/<raw sha256>.zst` (6). Read literally, for protected kinds the key is the hash of PRE-scrub bytes. DESIGN.md:710 separately says integrity checks compare transformed bytes.
- Code: capture.rs:477-479 runs `transform` then `authorize`, then slices the AuthorizedBody (capture.rs:~495-502); `Piece::from_authorized` (memory-core/src/manifest/schema.rs:325-350) computes `sha256 = manifest_hash(chunk)` over the authorized (scrubbed) chunk and sets `object = object_key(&sha256)`. So the key is the hash of the transformed bytes. Manifest records `sha256` (raw=transformed pre-encoding), `encoded_len`, `encoded_sha256` (both). Validation enforces `object == object_key(sha256)` (schema.rs:395).
- Encoding today is identity: capture.rs:21 "piece encoding is the identity (no zstd yet; `encoded_*` equal the raw fields)"; schema.rs:346-349 sets `encoding: Encoding::Zstd3`, `encoded_len: len`, `encoded_sha256: sha256`. Finding (medium): manifests say "zstd-3" and keys end `.zst` for bytes that are NOT zstd. Any reader that decompresses per the declared encoding fails; a later real zstd writer would 412 against these identity objects and adopt_stored them, leaving mixed encodings under one declared label. Nothing in the Encoding enum can express "identity".
- 412 handling: commit.rs:253-278 `upload_pieces`: on PreconditionFailed it GETs the stored object and records `StoredEncoding{encoded_len, encoded_sha256}` of the winner; `adopt_winner` (commit.rs:228-238) rewrites the descriptor via `Piece::adopt_stored` (schema.rs:386). `Manifest::verify_encodings` (schema.rs:920-935) checks descriptors against stored objects (MissingObject / EncodingMismatch). So two stored encodings of one key do not cause a reader digest mismatch: the manifest always records the winner's. Gap: adopt trusts whatever is stored; it does not check the winner decodes to the transformed bytes (reader digest of `sha256` after decode is the only check). A 412'd key whose stored bytes are corrupt or foreign is adopted silently.
- Rules change: planner.rs:178, 204, 232 return `Replay{RulesChanged}` when `remote.rules != input.rules` (also snapshot `previous_rules`); DESIGN.md:465 "a rules change starts epoch n+1 from byte 0". Because the key is the hash of scrubbed bytes, a stricter rule yields different bytes -> different key -> new object, new manifest. A privacy fix therefore DOES replace what the manifest points to. It does NOT delete the old leaky object: unreferenced objects stay (DESIGN.md:467, 19 decision 4; "No bucket lock", so deletion remains possible but the tool is "the reader project", unbuilt). Under DESIGN's literal order (key = hash of pre-scrub bytes) the failure would be real: same raw bytes -> same key -> 412 -> adopt the old, leaky winner. The code avoids it only by deviating from the text. Recommendation: amend DESIGN 6.2/7.3 to say "hash of transformed (post-scrub, pre-compression) bytes" and add a test: same raw input under two rule digests yields two keys.
- Real-world note: whole-stream `sha256` (capture.rs:513-523) is over the transformed body as well, consistent.
- Unknown: whether any protected-kind path hashes pre-transform elsewhere (I read only capture.rs 440-560). limits.rs has no hashing relevant to this.

## C3. Store fake fidelity: PARTLY CONFIRMED (reviewer right that divergences exist; the production commit loop tolerates them). Confidence medium-high.
Real R2 evidence (stored): docs/rust-rewrite/prototypes/P2-s3-client.md:22 "create Ok; repeat 412; GET ETag == PUT ETag; If-Match fresh Ok; stale 412; If-Match on missing key 412; GET missing 404"; raw: p2-s3-client/results/r2-os.jsonl lines 1-9 (also `etag_is_md5_of_body: true`). P11-commit-retry.md:78-83 and p11-commit-retry/r2-raw.json (889 samples, statuses only 200 x781 and 412 x108; zero 409; `stale_not_412: 0`, `create_exists_412: 20`, 60 races each A=200,B=412).
(a) If-None-Match:* on existing: 412 (20/20; P2 `create_again`). Fake: `(Fence::Absent, Some(_)) => false` -> PreconditionFailed. Same.
(b) stale If-Match: 412 (28/28). Fake: etag mismatch -> PreconditionFailed. Same.
(c) If-Match on missing key: real 412. Fake: `(Fence::Match(_), None) => return Err(StoreError::NotFound)` (tests/commit_protocol.rs HEAD, ~line 265). DIVERGES. daemon.rs FStore also returns NotFound (HEAD, lines ~97 of FStore put). Production: commit.rs:394-398 `Err(_) => {}` then verify GET for every non-Auth error, so both statuses take the same path; harmless in commit.rs. But environment.rs:63 documents NotFound as "(and a conditional write against a missing key)" which contradicts the measured 412.
(d) Concurrent conditional PUTs: real R2, 60 races: one 200, one 412, no 409 (r2-raw.json). Fake is single-threaded: no concurrency, "Foreign" effect injects a rewrite before the next request. Not modelled: simultaneous in-flight writes, 409. Production: no 409 variant in StoreError (environment.rs:59-83); a 409 from an adapter would have to map to Server (retries as offline) and for current.json is absorbed by the `Err(_)` -> verify path; for pieces/manifests it becomes `not_landed` (retry capture). No HTTP adapter exists in rust/crates yet (grep: ureq/rusty-s3/object_store appear only in deny.toml and README), so the real status mapping is untested in production code.
(e) Rewriting identical bytes: P2 shows ETag == md5(body); identical-bytes rewrite ETag unchanged is inferred, NOT measured on R2 (`etag_changed` in lost-reply suite compares v0->v1, different bodies). Fake: `write` always bumps a counter, so ETag changes (and has an explicit `Effect::Churn` "rewrites current.json unchanged, giving it a new ETag"). DIVERGES in the direction that real R2 would NOT churn, so Churn tests exercise a case that cannot occur with md5 ETags; conversely a stale-ETag ABA (identical content) cannot be detected on R2 but is harmless because current.json content is the same.
Other: fake has no Retry-After body/timeouts, no multipart, no 404-after-delete, no 409 delete race.
Official docs fetched this session:
- Cloudflare R2 S3 extensions, https://developers.cloudflare.com/r2/api/s3/extensions/ : PutObject supports If-Match / If-None-Match; concurrent `If-None-Match: *` "at most one request succeeds and every other request fails with a `412 PreconditionFailed`". No 409 or 404 documented for conditional PutObject.
- AWS S3, https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html : If-None-Match existing -> "412 Precondition Failed"; "You can also receive a `409 Conflict` response in the case of concurrent requests if a delete request ... succeeds before a conditional write"; If-Match mismatch -> 412, "You can also receive a `409 Conflict` response in the case of concurrent requests"; If-Match with missing object -> "404 Not Found". So on AWS S3 (c) is 404, on R2 measured 412: the fake matches AWS, not R2. Since the target is R2, the fake is wrong on (c); if the bucket ever moves to S3, 409 must be classified.
Unknown: R2 409 under concurrent delete (no deletes in design except a manual leak tool). Experiment: against a rust-acceptance/ prefix, run PUT identical body twice with If-Match and compare ETags; run 100 concurrent If-Match writers; If-Match after DELETE.

## C5. Memory bound: CONFIRMED the numbers; the "80 MiB" is a payload-only target, not evidence. Confidence high.
- DESIGN.md:595-597: "At most 2 hash or compress jobs run at once, and at most 8 uploads. The peak is therefore about 2 x 8 MiB raw plus 8 x encoded size, at most 80 MiB for incompressible data. [target, prototype P4]". Line 1146: resident peak target 128 MB; D18 (line 1281).
- P4 (prototypes/P4-synthetic-footprint.md:1-5): "This benchmark does not justify a change to the 8 MiB / 8 uploads defaults." Table row `8 | 8 | random | 83.89 | 135.12`; lines 41-42: "At 8 MiB / 8 random buffers, payload alone is 83.89 MB and process peak is 135.12 MB." Lines 44-47: "Target, not measured acceptance. Real daemon peak <128 MB ... None are passed here. Request-client copies, eight actual network PUTs, 30k index entries, fairness and native idle wakeups still need real implementation measurement."
- Arithmetic: 2x8 MiB + 8x8 MiB = 80 MiB = 83.89 MB (decimal); matches payload column. DESIGN's 80 MiB is therefore payload only and, because it assumes incompressible data, excludes the process baseline, HTTP client copies (a signed PUT may copy the body, doubling per upload), the index (30k sources), allocator slack. P4's 135.12 MB is a Python process (interpreter included, no baseline subtraction) so it over-states Rust but still exceeds 128 MB; a Rust daemon likely lands below, but unproven. Also Rust identity encoding today means encoded = raw (no compression yet), so the current code's bound would be 2x8 + 8x8 = 80 MiB raw regardless of data.
- Settling measurement: after the uploader exists, run the real daemon against the acceptance prefix with a synthetic backlog of random (incompressible) 8 MiB pieces across >=8 concurrent PUTs and a 30k-entry index, record peak RSS (e.g. /usr/bin/time -l on macOS, `VmHWM` on Linux) and compare to 128 MB; repeat with the chosen client (P2: rusty-s3+ureq vs object_store). A cheaper pre-check: allocate-only Rust harness holding 2 raw + 8 body buffers plus a 30k-entry index and an HTTP request copy, to find baseline.
