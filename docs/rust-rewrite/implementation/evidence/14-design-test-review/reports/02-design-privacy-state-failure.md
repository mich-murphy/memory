# Review 02: DESIGN.md sections 8-12, amendments A6/A7, supporting evidence

Scope read: DESIGN.md 650-1013, design-amendments-20261109.md, P7, P11 (skimmed), P12, challenge/03 and 04, implementation 19, and the code the sections describe (rust/crates/memory/src/{state,daemon,hook,watch,realfs}.rs, memory-core disposition.rs, privacy/{names,launch}.rs). Read-only. No cargo runs. Labels: (V) verified in repo or fetched source, (I) inference, (U) unverified/from memory.

## Verdict

The design is well reasoned and the state-write protocol is correct. The weak points are not the protocol but what happens around it: the "treat as missing" policy silently discards system-of-record data (parked list, learned roots), several documented behaviours are not implemented or not observable (logging, hint retention, startup jitter), the 15 min reconcile and the 3 h / 3-failure park rule are chosen, not measured, and a captive-portal class is mis-routed into a per-source park. Privacy is fail-closed at the policy table and in the type pipeline, but the read path opens by path with no identity re-check, so the "no symlink captured" claim (A4) is enforced only at walk time.

## Findings, most severe first

### F1. "Treat as missing" silently drops system-of-record state (medium-high, confidence high)
- DESIGN 9.1 classifies `status.json` (parked list) and `roots.json` (learned custom roots) as system of record. 9.2 says a failed checksum, short body or unknown version is "treated as missing"; for status "counters restart and the event is logged".
- Code: `daemon.rs:259-262` `open()` maps any `Loaded::Missing` or serde failure to `StatusBody::default()` with no log. A grep for `tracing::` in rust/crates/memory/src returns nothing, so the "logged" promise has no implementation. `roots.json` is not read anywhere yet.
- Scenario: power loss tears status.json; or a downgrade after a newer writer wrote schema 2 (`NewerSchema`). Daemon starts with empty parked list and `host_paused=false`. Owners parked for a foreign writer or repeated audit mismatch resume writing. The ETag fence re-parks foreign writers (one wasted conflict), but source-level parks (audit/readback/NonJson/Schema) restart their 3 h clock. For roots.json the same path would silently forget learned custom roots, which AGENTS.md says to preserve; a root forgotten means sessions under it are no longer captured until rediscovered, and nothing records that it happened.
- Also `index.json` parsing failure after a good checksum is treated as "rebuilt" without any counter (`daemon.rs:255`).
- Action: treat damage to a system-of-record file as an event with a persisted counter and stderr line, keep the damaged file as `*.corrupt-<n>`, and for roots.json keep one previous generation (write `.prev` before rename) or refuse to start with a distinct exit code. Never default silently.

### F2. Hook failures and read-side skips are invisible (medium, high)
- `hook.rs` returns a closed `HookResult` but `main_entry` discards it (`let _ = process(agent)`), by DESIGN 10.1 ("never prints"). Nothing is counted. `DirRefused`, `NoStateDir`, `OpenFailed`, `WriteFailed` all lose the hint, including launch evidence, which DESIGN 10.4 says is the one non-recoverable signal.
- `daemon.rs:scan_hints` skips an unreadable or unscannable hint file with `continue` and no counter (lines ~480-495). A hint file over `MAX_HINT_FILE` (64 MiB) is truncated by `take` and, once the stored offset exceeds the truncated length, `scan(bytes, start)` errors and the code restarts from 0 (re-reading and re-attaching old records).
- Interleaving (hook vs daemon env): launchd/systemd service env may lack `MEMORY_STATE_DIR`/differ in `HOME` from the agent's env. The hook then writes `<HOME>/.local/state/memory/hints`, the daemon reads another dir; every hint is lost silently and only the 15 min reconcile hides it. A5 fixes the default but both binaries honour the override independently.
- Action: let the hook append a 1-line counter to a second tiny file (`hook-errors`, O_APPEND) or, minimum, have `memory status` compare newest hint-file mtime with newest session activity; count daemon-side skipped hint files in status.

### F3. Hint retention vs concurrent hook: documented loss mode, no implementation yet (medium, medium)
- DESIGN 3.4 measures "write after unlink of a renamed hint file succeeds and is lost" (V). 9.1 says hint files are deleted after 7 days "and until every launch record is committed". No deletion exists in daemon.rs (V: grep `remove_file` finds none), so unbounded growth now, and the race is latent.
- Interleaving: (1) hook opens `D.jsonl` with O_APPEND; (2) daemon decides all records committed and unlinks `D.jsonl`; (3) hook `write(2)` lands on the unlinked inode, record lost, no error. UTC day rollover widens it: a hook started at 23:59:59.9 holds yesterday's name.
- Action: never unlink a file whose day is today or yesterday UTC; delete only files older than 7 days (the spec already says so, make the code test it), and never delete on "committed".

### F4. Failure classification: captive portal parks a source, which needs a human (medium, medium)
- DESIGN 11.2 puts non-JSON 200 (captive portal) in `Deterministic`, parked per source after 3 consecutive failures spanning at least 3 h (`disposition.rs:PARK_THRESHOLD`, `PARK_MIN_SPAN`). A captive portal is a property of the network, not the source: it is host-scoped and clears when the user leaves the hotel. A laptop on a captive network for 3 h parks sources (`RepeatedNonJsonResponse`) which then need `memory unpark`. Compare `Offline`, which retries forever with no park, the right disposition for it.
- Streak is in memory only (`OwnerRt.streak`, `daemon.rs:289-298`), though `disposition.rs` says "persisted by the shell". Any restart inside 3 h (launchd KeepAlive after a crash, a laptop reboot) resets `first_at`, so a genuinely deterministic fault that restarts the daemon never reaches the park rule. And the span uses monotonic time that excludes sleep (DESIGN 7.1), so a laptop asleep 10 h of a 12 h day needs far more wall time.
- `Local` (disk full, EACCES reading a source) retries forever at 15 min cap with only a counter; it is "retried forever" but counted, so not silently swallowed. A permanent EACCES on one source is not transient and is never parked (inference from 11.2 table).
- DESIGN 11.2 says "a daemon restart ... after a startup jitter of 0 to 60 s"; no such jitter exists in daemon.rs (V, grep). Backoff resets at restart by design, so a crash loop retries every startup (launchd throttles at 10 s; systemd start limit).
- Action: classify non-JSON 200 as `Offline`-like host-scoped (`PauseHost` with probe), persist the streak (count + first wall time) in status.json, treat EACCES/ENOENT-after-stat as deterministic.

### F5. Retry amplification: layered retries and no budget (medium, medium)
- AWS Builders' Library (fetched: builder.aws.com, the redirect of aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter): "retries at each layer multiply ... for low-cost control-plane and data-plane operations, our best practice is to retry at a single point in the stack"; and mitigate with "limiting retries locally using a token bucket". Google SRE, Addressing Cascading Failures (fetched via sre.google): "Limit retries per request", randomized exponential backoff, a per-process retry budget ("60 retries per minute", "if the retry budget is exceeded, don't retry; just fail the request").
- Here: in-commit rebase retries up to 4 (A6) x outer per-owner `Retry` with backoff x whatever the S3 client retries internally (P2 not checked here; I did not verify whether the chosen client has its own retry layer) x up to 8 concurrent uploads host-wide x 2 hosts. A6 explicitly records "shared retry token bucket ... unproven, not adopted". That is a defensible, evidence-noted deferral, but the multiplication is not bounded by a measured number. P11's real R2 probe was 889 requests, which is too small to show throttling behaviour at fleet scale; simulation was 100 owners.
- Backoff itself is sound: full jitter `uniform(1 s, ceiling)` is within the AWS recommendation (note the AWS post does not give the formula in the page; the formula is from the AWS Architecture Blog "Exponential Backoff and Jitter", not fetched here, (U)). Retry-After clamp [1 s, 15 min] prevents hot loops (V, `disposition.rs`).
- Action: record the S3 client's internal retry count and disable it (single retry point), and add an owner-count-independent token bucket before cutover.

### F6. Read path opens by path and does not bind the read to the admitted identity (medium-low, medium)
- A4 says "no file is captured through a link", enforced by `realfs::walk` never yielding symlinks. `realfs.rs:126` `File::open(self.path(source)?)` has no `O_NOFOLLOW` and no post-open `fstat` check against the walked dev/ino. Interleaving: walk admits `<root>/a/x.jsonl`; same-user process (a malicious agent skill/tool, the exact actor secret protections exist for) replaces it with a symlink to `~/.aws/credentials` or `~/.ssh/id_rsa`; capture reads the target and uploads it (Pi/Claude transcripts aren't scrubbed, and a plain file read bypasses the denylist because admission ran on the old path). Requires same-user write access under an agent root, so this is a privilege-neutral but real "fail-closed" gap; DESIGN 8.2 says the denylist is checked "against every identity in the chain" but this is checked at admission only.
- Action: open with `O_NOFOLLOW` (needs `rustix`/`libc` or std `OpenOptionsExt::custom_flags(libc::O_NOFOLLOW)` which needs the libc constant), then `fstat` and require dev/ino/kind equal the admitted ones. Add a test that swaps a file for a symlink between walk and read.

### F7. Directory-deletion hazard for the single-instance lock (low-medium, medium)
- `DaemonLock` flocks `state/daemon.lock` (V, `state.rs:156-175`). DESIGN 9.1 advertises that `index.json` "may be deleted". An operator who runs `rm -rf ~/.local/state/memory` while the daemon runs, then starts a second daemon: the second creates a new directory and new lock inode and acquires it; two daemons now write the same owners. The ETag fence and (A6) `known_ours` make this safe for R2 (the second looks foreign and parks the owner), but both then park, and both write index/status through renames into the same path (last writer wins).
- Other lock facts (V, flock(2) man page fetched): lock belongs to the open file description, is released when all duplicate descriptors close; Rust std opens with O_CLOEXEC so children do not inherit it (U, from memory). Crash while holding: kernel releases, no stale lock and no PID file, so PID reuse does not apply (correct design). On NFS, Linux emulates flock as fcntl byte-range locks (V); if BC-01's `$HOME` is on NFS the semantics change. DESIGN assumes one user per host (stated).
- Action: on each round, `fstat(lock fd).st_nlink > 0` and path inode equals fd inode, else exit "lock lost". Document "do not delete state dir while running".

### F8. Watcher assumptions (low-medium, medium)
- Verified OS semantics: inotify: identical successive events are coalesced if unread, so events cannot be counted; `IN_Q_OVERFLOW` always generated when the queue limit is exceeded; rename pairs are "inherently racy"; recursive watching needs a watch per subdir and a new subdir "may already contain files" (man7.org inotify(7), fetched). That matches DESIGN 10.2's mitigation (readdir on Create(Folder)). FSEvents `MustScanSubDirs/UserDropped/KernelDropped` mapping to `need_rescan()` is verified from notify source by challenge/03 (read, citing fsevent.rs:253-258), not re-verified here; my fetch of Apple's page returned only a title (U for Apple wording).
- Gaps in the implementation that DESIGN 10.4 does not state: (a) `FsWatcher::new` aborts if any root is absent (`watch.rs` `watcher.watch(root, ...)?`), so an agent that is not yet installed makes the whole watcher fail, and a root that appears later is never watched without restart; (b) events go over an unbounded `std::sync::mpsc::channel`, so "producer outruns consumer" shows up as memory growth in the daemon, not as a kernel overflow the design describes; the 10.4 table row is therefore not what the code does; (c) not yet wired into the daemon loop (19-watch.md "Remaining").
- Reconcile interval 15 min: backed only by cost (3.4: 360 ms stat walk for 24,127 files). There is no measurement of event loss on either host and no latency target tied to 15 min; report 08 line 178 says "interval to be measured" and challenge/03 M2 only argues cost. DESIGN 11.3's primary metric target (under 10 min on a reachable network) is shorter than the 15 min reconcile that is the only recovery for a lost event on a hookless agent, so the target cannot be met after a dropped event for Pi sessions. (I) Either the target or the interval is wrong.
- Action: an experiment, see below.

### F9. State write protocol: correct; documentation and tests gaps (low, high)
Verified against code (`state.rs`): `create_new` temp in same dir, `write_all`, `sync_all`, `rename`, directory `sync_all`; a failed fsync removes the temp and the next attempt writes a new file from scratch, which is exactly what Rebello et al. (USENIX ATC 2020, fetched abstract only; PDF text not extractable) say is necessary: after an fsync failure pages are marked clean on all three studied file systems (ext4, XFS, Btrfs), and retrying fsync on the same file can falsely succeed. The design never retries on the same descriptor (I). SQLite (atomiccommit.html, fetched) says directory sync is needed so a file "appear[s] in the directory following a power failure" and that on Mac `fullfsync` "guarantee[s] ... pushed out to the disk platter" but is "profoundly slow" with disk-controller reset, "not recommended" for general use. P12 measured 5-7 ms per durable write on APFS and two writes a minute, so using F_FULLFSYNC is affordable (V). Pillai et al. OSDI 2014 (abstract fetched): application crash-consistency protocols depend on file-system "persistence properties" that vary across six Linux file systems; the file-fsync-then-rename-then-dir-fsync sequence is the conservative one, so the design is correct on Linux (I; the specific table of ARVR behaviour per file system I did not read).
- That `File::sync_all` is `F_FULLFSYNC` on Apple targets is asserted in state.rs and P12 from the SDK header; I did not read the Rust std source (U).
- Gaps: (a) P7 itself says "No F_FULLFSYNC/fsync/rename/directory-fsync power-failure test"; A7 adds a crash-point property that models "drop between stage and publish", which tests rename atomicity at process level only, not power loss, and cannot (flush has no observable effect to a live process, as A7 itself says); durability is therefore asserted, not tested, which is unavoidable but should be stated as "assumed, verified by fault injection of errors only". (b) Linux ext4 costs and behaviour unmeasured (BC-01 ssh failed twice, P12 "Not measured"). (c) `publish` returns an error if the directory fsync fails after a successful rename; the new file is already visible, callers must treat as "maybe durable" and not re-stage assuming the old one is intact (daemon surfaces `RoundError::State`; fine). (d) The sweep removes temps only at startup; a failed write in a long-running daemon removes its own temp (V).
- SQLite vs small classified files: the repo does not contain a head-to-head. The evidence is indirect: Go's SQLite tables were a work queue and four state machines (reports/02 items 1, 10), which the design deletes; what remains is three small documents written 2x/min. SQLite would also give atomic commit via its documented rollback journal, but for three small derived documents the custom envelope (header with length and SHA-256, 8 ms validation of 20 MB per P7) is cheaper to reason about. I consider the decision justified for index/status/roots by the removal of the queue, not by any measurement; the cost of the choice is F1 (no previous generation, no recovery of damaged documents), which SQLite's journal would not have either, so it does not argue for SQLite.
- Minor: P7's SHA-256 claim "CRC32C not collision-resistant" is irrelevant for integrity against accidental damage; SHA-256 at 8 ms/20 MB is fine but is selected because it detects only accidental, not adversarial, change (no key) (V, P7 says so).

### F10. DESIGN text mismatches (low, high)
- 8.4 says "at most 8 exact names" and lists nine; code has a 9-element `ENV_ALLOWLIST` with a cap of 8 (`launch.rs`), so a 9th allowlisted var is dropped depending on environment order, an unspecified result.
- 9.1 "`state/tmp/` | SQLite backups only. Emptied at start" while the machine-id file `state/machine_id` (`StateFile::MachineId`) is implemented but not in the 9.1 table, and 9.1 prose says machine ids are copied into `config.toml`. Two homes for the machine id; `Config` requires one, `StateDir::create_machine_id` can create another. If both exist and differ, owner keys fork. Not reconciled in the text (I; I did not trace the caller).
- 11.5 "A corrupt index is rebuilt, never a crash loop" holds in code; "rebuild" currently only empties `locals` and relies on adopt (9.3), whose per-source cost (15 s CPU per 4 GB) is a measured arithmetic, not an end-to-end run.

## Privacy (section 8): fail-closed assessment

Sound: type-level `Authorized<Redacted<Bytes>>` for PUT; `UnknownKind`/`UnknownOwner` withheld, rules-digest mismatch withholds; `is_credential` fails closed if the suffix regex cannot compile (`names.rs`); `safe()` returns false if the value regex fails, so launch values become `[redacted]`; the daemon re-sanitises hint launch fields on read (`scan_hints` calls `sanitize_launch` again), a second layer; errors carry no values; positional args become `[redacted]`. OWASP Logging Cheat Sheet (fetched) lists access tokens, passwords, keys, connection strings as data to remove or mask and asks that logging failures not "allow information leakage"; the design's closed-error enums and info-level logs without paths match that.

Not fail-closed or under-specified:
1. F6 above (admission not bound to the read).
2. `is_secret_name` on values (`launch.rs:safe`) uses only token/key/auth segments and a handful of substrings. A model-looking value such as `sk-ant-api03-AbC...` contains no such segment, matches SAFE_VALUE, and would pass in `--model`, `--session`, `--config` or `ANTHROPIC_MODEL`. Argv is dropped at the hook (A3), but env facts still flow, and `sanitize_launch` still guards any argv reaching it. Residual: a user who puts a key into an allowlisted variable by mistake. Low severity, medium confidence; fix: also reject values over a high-entropy or `sk-`/`ghp_`/`AKIA` shape test, or restrict `--model` values to a known model-name charset without long random tails.
3. Directory denylist matching is case-sensitive (`path.contains("/.ssh/")` while `basename()` lowercases), and macOS default APFS is case-insensitive: `.SSH/known_hosts` would not match the dir rule (key file names still match). Only reachable if a root or identity chain goes there; low.
4. The denylist is incomplete by design (no `.p12/.pfx/.jks/.keystore`, `.dockercfg`, `*.tfvars`, service-account JSONs, `kubeconfig`). It is a secondary control; the primary control is "unknown kind is withheld", so this is low. State it as a denylist, not a guarantee.
5. 8.5 does not enumerate failures in `transform::apply` (panic, oversized protected JSON beyond a depth/size bound) beyond `MalformedProtected`; the parser rejections listed are closed. A panic in the capture task: unspecified whether the daemon aborts (exit nonzero, restart) or continues with the file unwritten. Need an explicit rule and a test.
6. Hint paths (`transcript_path`, `cwd`) are treated as untrusted (8.2); good.
7. Config scrubbing is by basename list of eleven names; a config under any other name with embedded secrets (e.g. `config.local.toml`) is `UnknownKind` and withheld (V per 8.2); fine.

Residual risk, precisely (plaintext bucket accepted): any holder of any one of the Cloudflare account, either host, or either host's R2 token reads every stored transcript and every non-scrubbed content in it; transcripts are never scrubbed, so a secret pasted into a conversation, or printed by a tool the agent ran (`cat .env` output, `env`, curl responses with bearer tokens), is stored verbatim and indefinitely, and the "no bucket lock" control relies on a human finding it afterward. Config/credential scrubbing protects only files, not transcript text. Neither OWASP nor the design offers a transcript redaction; the design states this as accepted.

## What is sound, briefly
- Lock choice: flock via std `File::try_lock`, kernel release on death, no PID file: standard, avoids PID reuse and stale-lock cleanup (flock(2) fetched).
- Single-writer-per-owner enforced by key plus ETag, with real R2 evidence (28/28 stale ETags rejected, 60/60 race winners) in A6.
- Atomic-write sequence and "never retry fsync on the same file" are right.
- Retry classes separate throttling, offline, auth, deterministic; full jitter and Retry-After clamp.
- Status states "up to date as of <time>, never all captured".

## Open questions and experiments
1. Is 15 min safe for hookless sources? Run `notify` on a throwaway temp tree on the Mac with a stress writer (not real sessions), count events vs actual file changes under 15k watched dirs; record `need_rescan` frequency. Settles interval and the 11.3 target conflict.
2. Does damage to status.json lose parked state in practice? Unit test: write status with a park, corrupt one byte, start the daemon, assert on parked list and that an event is emitted (currently expected to fail on the event).
3. Symlink swap between walk and read: test in a temp dir that replaces a walked file with a link to a decoy "credential" and checks it is not captured (expected fail today).
4. Does the chosen S3 client retry internally? Read the P2 client config; if yes, A6's retry count is multiplied.
5. Does `File::sync_all` on the pinned toolchain issue `F_FULLFSYNC` for directories and files? `dtruss` or read the pinned std source in the Nix store.
6. Is the state dir ever on NFS on BC-01? `df -T $HOME` over SSH (blocked: agent has no identities).
